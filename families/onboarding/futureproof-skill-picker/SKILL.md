---
name: futureproof-skill-picker
description: |
  Reads a client's HyperTuned business memory, ranks the 145-skill FutureProof
  catalog (embedded in this skill) against the pains the client named in their
  own words, and surfaces the best 10 with a one-line, pain-tied reason each —
  then runs one live, plans the rest, and routes anything unmatched into a lane.
  Use when the user says "which skills fit this client", "pick the top 10 skills",
  "run the skill picker", or right after the onboarding interview finishes. For
  matching a client to skills that already exist and running one live, not for
  building a new skill or a custom feature — route unmet needs to futureproof-brd.
---

## Words used here

- **HyperTuned memory**: the 10-section write-up the onboarding interview produced about one client. Call it "the memory". After you connect, look for it in the "User Knowledge" section of the connect result.
- **The catalog** — the 145 FutureProof skills that already exist, listed in full in the **Catalog index** at the end of this skill.
- **A pain** — a problem, a bottleneck, or a task the client repeats. Anything a skill could fix or speed up.
- **Match text** — a catalog entry's one-line summary: a capability gist plus a "Use when…" trigger. You rank a skill by its match text.
- **The BRD** — a Business Requirements Document, the write-up used to build something new when no skill fits.

## Step 1: Connect to FutureProof

```
FutureProof:connect(skill="futureproof-skill-picker")
```

After you connect, look in the "User Knowledge" section of the result. The client's business memory is there as JSON text with a `business_memory` field. The onboarding interview saved it with `save_context`. The result has no `universal_context` field, so do not look for one.

> **Returning user check:** If `recent_sessions` shows the picker already ran for
> this client, open with what was recommended last time and ask whether to
> re-rank against updated pains or continue an earlier plan. Otherwise run the
> full ranking below.

**Load the memory before you rank anything.** Confirm you are working one client at a time. If the memory document is already in this chat, use it. The user may paste it, or the onboarding interview may have written it earlier in this chat. A memory saved in the last minute may not show in "User Knowledge" yet. If the interview just saved it, wait one minute and connect again. If you still find no memory, stop. Run the **futureproof-onboarding-interview** skill first. Then come back and run this skill. Read all 10 sections before ranking.

## Step 2: Pull the client's pains

1. Read **Section 10, "Where the gaps are"** first. It is the client's own list of weak points — the strongest pain signal.
2. Read **Section 4, "What ships"** next. It is the work the client repeats for money — the second-strongest signal.
3. Write each pain as one short line in the client's own words.
4. Scan Sections 1, 2, 3, 5, 6, 7, and 9 for more pains.
5. Set **Section 8, "How it sounds"** aside. It is the client's voice — used in Step 5, not for ranking.
6. List every pain you found. Do not rank yet.

## Step 3: Rank the catalog against the pains

Rank against the **Catalog index** at the end of this skill — never against outside files or a skill's name alone. Each catalog line has two parts: a **capability gist** (what the skill makes) and a **"Use when…" trigger** (example client requests).

1. For each pain, find skills whose **trigger** matches that pain. Weight these matches highest — the example requests are the sharpest signal.
2. Next, match the pain against the **capability gist**. Weight these second.
3. Give each skill a fit score for how well it answers the client's pains.
4. Reference every skill by the **name shown in the Catalog index** — that name is how the client invokes it.

## Step 4: Show the top 10

1. Pick the 10 highest-scoring skills across all the pains.
2. Write one line for each: its catalog name plus why it fits.
3. Tie each reason to a pain the client named, in the client's own words.
4. If fewer than 10 fit, list only the ones that fit. Do not pad the list.
5. Show the list to the client before you run anything.

## Step 5: Run one skill live

1. Pick the single best-fit skill from the top 10.
2. Run it on the client's **real input**, not a made-up sample.
3. If the skill makes content, write it in the client's voice from **Section 8**.
4. Show the client the finished output. One real win on real input proves value on the spot.

## Step 6: Plan the rest

1. For each remaining skill in the top 10, write a one-line plan: the input it needs and the output it produces.
2. Order the plan by which pain matters most to the client's goal in **Section 5**.
3. Hand the plan to the client or the account manager.

## Step 7: Route the gaps to the BRD

1. List every pain that no skill matched.
2. Sort each unmet pain into exactly one lane:
   - **Lane 1** — an existing skill actually covers it after a second look. Close it now by running that skill.
   - **Lane 2** — no skill fits, but one is worth building. Log it as a build request.
   - **Lane 3** — the client needs a true custom build.
3. Hand every Lane 2 and Lane 3 item to the **futureproof-brd** skill. It runs the EAD gate and writes the BRD for the dev team.

## Step 8: Propose Experiments

> **Always call save_experiment — never skip.** If no explicit test emerged, test
> the most uncertain ranking choice you made this session.

```
FutureProof:save_experiment(skill="futureproof-skill-picker", experiment={
  hypothesis: "[e.g. 'Weighting Section 10 gaps 2x over Section 4 repeated-work produces top-10 lists the client rates more relevant']",
  variants: ["control: equal weight across pain sources", "variant: gaps weighted highest"],
  measurement: "[e.g. client-confirmed relevance of the top 10, across the next N clients]",
  expected_impact: "[e.g. more of the top 10 get adopted; fewer Lane-1 'you missed one' corrections]"
})
```

## Step 9: Request Research

> **Research must be client-specific.** Only request research if a real pain had
> no good match and you suspect the catalog gap is worth closing for this niche.

```
FutureProof:request_research(skill="futureproof-skill-picker",
  query="[e.g. 'Common repeatable workflows for <client's niche> that no general business skill covers']",
  reason="[e.g. 'Two of the client's Section 10 pains matched nothing; confirm whether a new skill or a custom build is warranted']"
)
```

## Step 10: Save Session

> **Session summary must be fact-dense:** the client, their top pains, the top-10
> skills chosen, which skill was run live and its result, the plan order, and every
> unmet pain with its lane. End with **"Next session defaults: [3-5 things to
> pre-fill on next connect()]"**.

```
FutureProof:save_session(skill="futureproof-skill-picker", session={
  summary: "...[fact-dense: client, pains pulled, top 10 with pain-tied reasons, live-run result, plan order, unmet pains by lane, BRD handoffs. End with: Next session defaults: ...]",
  outcomes: [
    "Top pains: [the pains pulled from Sections 10 and 4]",
    "Top 10: [the chosen skill names]",
    "Ran live: [skill run + one-line result]",
    "Routed to BRD: [Lane 2/3 needs handed off]"
  ],
  metadata: {}
})
```

## Verification

You are done when you have shown the top 10 with a pain-tied reason for each, run one skill live on the client's real input, left a one-line plan for the rest, sorted every unmet pain into Lane 1, 2, or 3, and saved the session.
